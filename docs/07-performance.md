# Цель 7 (дополнение): Задержка DNS — измерение и оптимизация

> Задача: панель показывала среднюю задержку ~2000 мс, тогда как отдельные строки лога пересылаемых запросов — 3–45 мс, кэшированных ~0.1 мс. Сначала измерение, потом исправления.

---

## 1. Измерение: что на самом деле составляло «среднее»

Разбивка по статусам на копии реальной БД разработчика (`reqko.db`, 4016 строк):

| Статус | Доля | Средняя задержка | Вклад в общее среднее |
|---|---|---|---|
| FORWARDED | 76.0% | 143.46 мс | 109 мс |
| CACHED | 17.2% | 0.09 мс | ~0 |
| BLOCKED_* | 6.7% | ~0.1 мс | ~0 |
| **ERROR_UPSTREAM** | **0.1% (5 строк)** | **1 456 335 мс (до ~60 мин)** | **1813 мс** |
| **Итого (среднее)** | | **1922 мс** | |

**Вывод:** 94% «среднего» создавали 5 строк (0.1%) — отказы апстримов (последовательный перебор с полным таймаутом 2 с на каждого: 4 с на пару; часы — остановки цикла/сон машины). Поэтому:

- среднее больше не главное число; в `GET /api/v1/stats/summary` появились перцентили **p50/p95/p99/max** по группам: `latency_ms.upstream` (FORWARDED + ERROR_UPSTREAM — реальные обращения к апстриму), `latency_ms.cached`, `latency_ms.blocked` (блокированные/кэш учитываются отдельно и не размывают и не прячут upstream-задержку);
- в `/health` добавлен `event_loop_lag_ms` — максимум дрейфа `sleep(0.1)` за последнюю минуту (600 выборок): так видно «залипание» цикла событий;
- запросы медленнее 500 мс пишутся в лог как WARNING с именем, апстримом и числом попыток (`SLOW_QUERY_MS`, `dns/pipeline.py`);
- плитка панели теперь показывает **Latency p95 (upstream)** вместо среднего.

## 2. Исправления

| Изменение | Файл | Эффект |
|---|---|---|
| Апстримы опрашиваются **гонкой**: первый валидный ответ побеждает, остальные отменяются | `dns/upstream.py` (`query_upstream`) | мёртвый первый апстрим больше не добавляет свой таймаут к каждому запросу |
| Circuit breaker: 2 подряд неудачи → апстрим помечается нездоровым на 30 с; когда нездоровы все — пробуются все (чёрный блэкаут невозможен) | `UpstreamHealth` | здоровый апстрим предпочтителен; неудачей считается завершившийся таймаут/ошибка, а не отмена проигравшим в гонке (медленный, но рабочий апстрим остаётся доступен) |
| Таймаут апстрима по умолчанию 2.0 → **1.5 с** (`REQKO_UPSTREAM_TIMEOUT`) | `config.py` | быстрее отказ при полном недоступности |
| **Serve-stale (RFC 8767)**: при отказе всех апстримов истёкшая запись кэша отдаётся с TTL 30 с вместо SERVFAIL | `dns/cache.py` (`get_stale`, `build_response(override_ttl)`), `dns/pipeline.py` | клиенты продолжают получать ответы во время аварии апстрима |
| Предупреждение о медленных запросах ≥ 500 мс (имя, апстрим, попытки) | `dns/pipeline.py` | хвост задержек виден в логе |

**Не применено (измерение не подтвердило):**

- *Переиспользование UDP-сокетов апстрима*: создание сокета на запрос стоит ~1 мс — на фоне RTT сети и гонки это не фактор (здоровый путь p50 10–35 мс в бенче при искусственной задержке фейка 0–5 мс, `scripts/bench_dns.py`). Мультиплексный клиент с демуксом по ID — возможная будущая оптимизация.
- *Prefetch популярных записей*: кэш-хиты стоят 0.09 мс; prefetch не решает измеренную проблему (хвост апстрима) и добавляет фоновый трафик. Отложено.

## 3. До/после (scripts/bench_dns.py, 100 запросов, concurrency 10)

Сценарий: первый апстрим — «чёрная дыра» (привязан, не отвечает), второй — фейк с задержкой 5 мс; все имена уникальны (мимо кэша).

| Метрика | До | После | Ускорение |
|---|---|---|---|
| p50 | 2023.8 мс | **11.5 мс** | ×176 |
| p95 | 2040.0 мс | **14.4 мс** | ×142 |
| p99 | 2042.9 мс | **15.1 мс** | ×135 |
| max | 2043.2 мс | **15.3 мс** | ×134 |
| среднее | 2023.8 мс | 11.7 мс | ×173 |
| Пропускная способность | 5 qps | **729 qps** | ×146 |

Пояснение: «до» каждый запрос ждал полный таймаут мёртвого первого апстрима (2.0 с) и лишь потом шёл ко второму; «после» оба опрашиваются одновременно — побеждает ответ второго через ~5 мс.

Перцентили на реальных данных (см. раздел 1): `p50`/`p95`/`p99` отделяют хвост отказов от типичного пути; `avg_latency_ms` остался в ответе API только для совместимости.

## 4. Как воспроизвести

```bash
# автономный сценарий: подъём резолвера in-process с мёртвым первым апстримом
python scripts/bench_dns.py --selfhosted --n 100 --concurrency 10

# против уже запущенного сервера
python scripts/bench_dns.py --port 5454 --n 200 --concurrency 20
python scripts/bench_dns.py --port 5454 --n 200 --cached   # только кэш

# наблюдаемость
curl http://127.0.0.1:8080/health | jq .event_loop_lag_ms
curl -H "Authorization: Bearer ..." http://127.0.0.1:8080/api/v1/stats/summary | jq .latency_ms
```

Serve-stale покрыт интеграционным тестом `test_upstream_failure_serves_stale_cache_entry`: запись кэша истекает, апстрим гасится — ответ приходит из кэша с TTL 30 (а не SERVFAIL).
