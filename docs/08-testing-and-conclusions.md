### 2.3. Память (NFR-02) и 10-минутный soak

**Поправка v2:** цифры v1 (4.68–4.80 MiB) измеряли не сервер, а `.venv`-редиректор `python.exe` (Popen возвращает PID заглушки, реальный интерпретатор — её дочерний процесс; netstat подтверждает владельца портов). Корректные замеры выполняются по PID реального сервера.

Windows, `GetProcessMemoryInfo(PROCESS_MEMORY_COUNTERS_EX)` (PID 10176, 78 216 правил; evidence `08-rss.txt`):

| Точка замера | PrivateUsage (commit) | WorkingSet | PeakWorkingSet |
|---|---|---|---|
| Правила загружены, idle | **44.03 MiB** | 56.88 MiB | 70.07 MiB |
| Сразу после burst 15 000 запросов (c=300) | **55.32 MiB** | 68.02 MiB | 70.07 MiB |
| После 10-минутного soak | **56.52 MiB** | 67.52 MiB | 70.07 MiB |

| Точка замера | VmRSS | VmHWM |
|---|---|---|
| Правила загружены, idle | 61.8–62.6 MiB | 70.2–70.4 MiB |
| После load-burst (550 запросов) | 62.66 MiB | без изменений |

Soak-тренд (Windows, 20 qps, 600 с, 8909 запросов, 0 ошибок): PrivateUsage 55.33 → 56.50 MiB (**+1.16 MiB**), WorkingSet −0.39 MiB — рост на уровне аллокаторного шума, утечки нет.

**NFR-02 (≤ 200–350 МБ при 100k+ доменов): выполнен с запасом ~4–8×** на обеих ОС. Хелпер замера — `scripts/bench_soak.py` (`memory_snapshot`).

### 2.4. Отказоустойчивость (NFR-03) и переполнение очереди

- **Мёртвый апстрим** (evidence `08-resilience.txt`): единственный фейковый апстрим убивался после прогрева кэша — истёкшая запись отдавалась из кэша **за 4.6 мс** (serve-stale, RFC 8767), последующие запросы получали быстрые ошибки без зависаний, `/health` оставался `ok`.
- **Circuit breaker в бою** (evidence `08-queue-overflow.txt`): после burst 15 000 запросов Quad9 включил защиту от флуда; 2 подряд таймаута → оба апстрима помечены нездоровыми на 30 с (WARNING в логе), клиенты продолжали получать ответы (SERVFAIL, без зависаний), после кулдауна — автоматическое восстановление до 3.4–4.0 мс без перезапуска.
- **Переполнение очереди**: burst 15 000 запросов при concurrency 300 (ёмкость очереди 10 000): **0 dropped_events**, все ответы получены, очередь после — 0. Писатель-батчер успевает; путь переполнения (QueueFull → счётчик → DNS продолжает отвечать) покрыт юнит-тестом (`test_storage_writer.py`). Достичь реального переполнения с одного хоста не удалось — это честный результат, а не пропуск.
- Изоляция горячего пути: SQLite-запись — в executor'е батчами, анализ предложений и парсинг списков — в executor'е, метрики — O(1) в памяти; `/metrics` и REST API — отдельные приложения (NFR-03, NFR-07).

## 3. Безопасность (NFR-04)

### 3.1. DNS-контур (evidence `08-security-dns.txt`)

Фузз **10 000 пакетов** за 0.94 с: случайные байты, абсурдные заголовки, мутации реальных запросов, compression-pointer атаки (самоуказатели, циклы, цепочки), имена > 253 октетов, гигантские QDCOUNT/ARCOUNT. LIVENESS-проба каждые 500 пакетов (max 11.6 мс), финальная проба 5.2 мс, `/health` — ok. **Сервер ни разу не упал и не завис.**

ACL (REFUSED из недоверенных сетей), rate limit (429/REFUSED), отказ ANY — покрыты интеграционными тестами (`test_servers.py`, `test_pipeline.py`).

### 3.2. API-контур (evidence `08-security-api.txt`) — 11/11 проверок

401 (нет/неверный токен), 403 (read-скоуп на админ-эндпоинтах, клиент-скоуп вне расширения — матрица 403 покрыта pytest), 429 при брутфорсе (pytest), SQL-инъекции во всех параметрах и сегментах путей → 200/400/404/405 (никогда 500; все значения — через связанные параметры, f-string SQL интерполирует только кодовые фрагменты из фиксированных allowlist), path traversal на `/panel` → всегда 404, тело 2 MiB → 400 без 5xx, security-заголовки (CSP, X-Content-Type-Options, X-Frame-Options, Cache-Control, Referrer-Policy) на всех проверенных ответах, включая 404.

## 6. Известные ограничения

1. **First-party реклама** (баннеры на доменах самого сайта) не блокируется DNS вообще — принципиальное ограничение технологии; для этого существует браузерное расширение.
2. **Адаптивные предложения**: точность ≈ 30% (8/27) на реальных данных при дефолтных настройках; сигнал keyword точен (8/9), но fallback/burst дают много false positives. Ручной approve обязателен, auto-approve выключен по умолчанию.
3. **Браузерная блокировка в Firefox Android не проверялась** (NOT RUN: нет устройства); ручная проверка блокировки выполнена только вручную в десктопном браузере.
4. **Ручная браузерная верификация** (реальные сайты, скриншоты «до/после») выполнялась вручную и не автоматизирована.
5. Локальный Trivy-скан образа был единственным местом, где setuptools 70.3.0 «существовал» (SBOM-файл pip 26.3) — устранено удалением файла на стадии сборки (см. §3.3 и `08-trivy-origin.txt`); свежеподнятая база `python:3.11.9-slim` при будущих пересборках может приносить новые версии bundled-пакетов — гейт CI это контролирует.
6. Perf-числа получены на Windows-хосте разработчика с loopback-клиентом; при c≥10 потолок ~2300 qps ограничен клиентским процессом бенчмарка, а не сервером.
7. `REQKO_LOG_*`, метрики и `/health` не защищены от long-term log growth сверх retention — ограничение по дизайну (retention 7 дней по умолчанию).

## 8. Направления будущей работы

1. Мультиплексируемый клиент апстримов с пулом сокетов и демуксом по ID (измеренная цена сокета-на-запрос ≈ 1 мс — выигрыш мал, но на 10k+ qps станет заметен).
2. Prefetch популярных записей перед истечением TTL (отложено: не подтверждено измерением).
3. DoH/DoT к апстримам (шифрование исходящих запросов).
4. Автоматизация браузерных проверок расширения (Playwright + загрузка распакованного расширения).
5. Уточнение эвристик предложений на большем корпусе логов (снижение FP ниже 30%).
