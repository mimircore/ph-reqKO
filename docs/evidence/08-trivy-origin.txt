== 2. layer forensics ==
Layer 8 of 9 = the RUN layer 'pip install wheel && upgrade pip/setuptools && uninstall wheel'.
Extracted the layer tar (docker save -> manifest.json -> blobs/sha256/9da744e7..., gunzip,
sha256 == 8e71541b...): it contains setuptools-84.2.1.dist-info + a whiteout for the base's
setuptools-65.5.1.dist-info. NO file anywhere in the layer carries version 70.3.0.

== 3. root cause: pip's own CycloneDX SBOM ==
grep of the layer for the literal '70.3.0' finds exactly two files:
  usr/local/lib/python3.11/site-packages/pip/_vendor/bom.cdx.json
      -> 'pkg:pypi/setuptools@70.3.0' (pip 26.3's CycloneDX SBOM of its BUILD-time deps)
  usr/local/lib/python3.11/site-packages/pip/_vendor/vendor.txt
      -> 'setuptools==70.3.0' (plain-text list of the same)
pip 26.3 does NOT vendor setuptools code: pip/_vendor contains 705 entries, none named
setuptools. The installed setuptools is 84.2.1 (>= fix 78.1.1). Trivy's SBOM analyzer parses
the third-party bom.cdx.json and reports its build-time 'setuptools 70.3.0' component as an
installed package — exactly what Trivy's own log hints at ('Third-party SBOM may lead to
inaccurate vulnerability detection'). The finding was introduced by the previous remediation
(upgrading pip to 26.3, which began shipping this SBOM file).

== 4. resolution (real fix, no .trivyignore) ==
The runtime stage now removes the inaccurate record in the same layer:
  rm -f /usr/local/lib/python3.11/site-packages/pip/_vendor/bom.cdx.json
The file is pip-internal documentation, never read at runtime; the image's real setuptools
is 84.2.1. Result: trivy exits 0 with the CI policy UNCHANGED
(--severity HIGH,CRITICAL --ignore-unfixed):
