# Цель 6 — Безопасный удалённый доступ (ph-reqKO)

> Практическое руководство по удалённому доступу к DNS (53/udp+tcp) и веб-панели ph-reqKO.
> Основание: [docs/02-requirements.md](02-requirements.md) (FR-17, NFR-04, NFR-08), [docs/03-architecture.md](03-architecture.md) (разделы 8, 11).

## 1. Модель угроз

| Угроза | Сценарий | Последствия | Защита в проекте |
|---|---|---|---|
| **Открытый резолвер (open resolver)** | Порт 53 опубликован на интерфейсе, доступном из интернета; любой сканер находит резолвер | DNS amplification/reflection-атаки от вашего имени, ваш IP попадает в чёрные списки, кража трафика | По умолчанию `REQKO_DNS_BIND=127.0.0.1` (только localhost); при публикации в LAN — ACL `REQKO_ALLOWED_NETWORKS` (только частные диапазоны), отказ в ANY, per-client rate limiting |
| **Утечка токена** | Токен из `.env` попал в git, скриншот, лог; или read-токен передан по HTTP | Полный доступ к статистике/журналу (admin), изменение правил блокировок | `.env` в `.gitignore` и `.dockerignore`; токены передаются только как `Authorization: Bearer` по HTTPS (TLS через Caddy); хранятся в БД только SHA-256 хеши; `docker-compose.yml` не стартует без `REQKO_ADMIN_TOKEN`/`REQKO_READ_TOKEN` (`:?` синтаксис) |
| **Brute force токена** | Перебор значений заголовка Authorization | Подбор admin-токена | Per-IP лимит неудачных аутентификаций: 10 неудач за 60 с → 429 (`REQKO_AUTH_FAILURE_LIMIT/WINDOW`); длинные случайные токены (`openssl rand -hex 32`) делают перебор нереальным |
| **Компрометация контейнера** | Эксплуатация уязвимости в приложении | Чтение/изменение файлов хоста | `read_only: true`, `cap_drop: ALL`, `no-new-privileges:true`, non-root UID 10001, `pids_limit`/`mem_limit`/`cpus`, только именованный том `/data` |
| **Перехват панели/API в LAN** | Сосед по сети читает трафик 8080 | Кража Bearer-токена | Порт 8080 **не публикуется** на хост; наружу — только HTTPS 443 через Caddy (HSTS, внутренний CA для localhost/LAN); API в изолированной сети `backend` (internal: true) |

## 2. Рекомендуемые профили доступа (от наиболее к наименее безопасному)

1. **Только LAN (по умолчанию).** DNS публикуется на интерфейсе домашней сети или вообще остаётся на `127.0.0.1` (по умолчанию); панель открывается только с самого хоста. Удалённый доступ не настраивается вовсе. Рекомендуется как базовый.
2. **VPN (рекомендуемый удалённый доступ).** Клиенты подключаются по WireGuard и через VPN-туннель получают DNS (53) и панель (через прокси). Ничего не публикуется в интернет напрямую. Настраивается профилем `vpn` (см. раздел 3).
3. **Публикация DNS в интернет — не рекомендуется.** Если без этого никак: привязывайте `REQKO_DNS_BIND` строго к LAN-интерфейсу (не `0.0.0.0`), оставьте ACL и rate limit включёнными, понимайте риск amplification-атак.

## 3. Удалённый доступ через WireGuard (профиль `vpn`)

### 3.1. Что уже настроено в `docker-compose.yml`

Сервис `wireguard` (образ `linuxserver/wireguard:1.0.20260223`, тег зафиксирован) объявлен под профилем `vpn` и подключён к внутренним сетям `backend` и не-internal `edge`. Наружу публикуется только UDP-порт WireGuard, **по умолчанию — на `127.0.0.1`**:

```yaml
ports:
  - "${REQKO_WG_BIND:-127.0.0.1}:51820:51820/udp"
```

То же касается HTTPS-прокси: `REQKO_HTTPS_BIND` по умолчанию `127.0.0.1` (`443:8443`). **Для реального удалённого доступа обе переменные (`REQKO_WG_BIND`, `REQKO_HTTPS_BIND`) нужно переопределить в `.env`** — на LAN-адрес хоста или `0.0.0.0` при публикации через маршрутизатор (см. раздел 3.4 и чек-лист).

Запуск:

```bash
mkdir -p docker/wireguard          # конфигурация WireGuard
cp .env.example .env               # и заполнить токены
docker compose --profile vpn up -d
```

WireGuard-клиенты, подключившиеся к туннелю, попадают в сеть `backend` и используют контейнер reqko как DNS-сервер по его фиксированному адресу **172.28.0.10:53** (стандартный порт, см. раздел 3.3), а панель — через HTTPS-прокси.

> **НЕ ПРОВЕРЕНО**: запуск профиля `vpn`, генерация ключей и реальное VPN-подключение не выполнялись на машине разработки (нет Docker). Шаги ниже соответствуют документации linuxserver/wireguard и стандартной практике WireGuard, но не воспроизводились здесь.

### 3.2. Генерация серверной конфигурации (один раз)

```bash
# ключи сервера
docker compose --profile vpn run --rm wireguard bash -c \
  "wg genkey | tee /config/server/privatekey | wg pubkey > /config/server/publickey"
```

Затем создать `docker/wireguard/wg0.conf` по образцу из документации linuxserver/wireguard (`server`-блок с `ListenPort = 51820`, `PostUp/PostDown` для iptables MASQUERADE) и peer-блоками для каждого устройства. Точный шаблон зависит от вашей подсети (например, `10.13.13.0/24`).

### 3.3. Подключение телефона / ноутбука

Конкретная схема DNS-over-VPN (реализована в `docker-compose.yml`):

- контейнер `reqko` слушает **53/udp+tcp** напрямую (без root — sysctl `net.ipv4.ip_unprivileged_port_start=0`);
- ему назначен **фиксированный IPv4 `172.28.0.10`** в сети `backend` (subnet `172.28.0.0/24`, ipam);
- контейнер `wireguard` подключён к той же сети `backend`, поэтому маршрутизация от туннеля до резолвера идёт внутри docker-сети (в `wg0.conf` сервера нужны `PostUp`/`PostDown`-правила форвардинга из документации linuxserver/wireguard).

1. Установите WireGuard-клиент (iOS/Android/Windows/macOS — официальные клиенты).
2. Сгенерируйте peer-конфигурацию (ключи клиента, `AllowedIPs = 10.13.13.x/32`) и добавьте её в `wg0.conf` сервера; для телефона удобно отсканировать QR-код (`qrencode -t ansiutf8 < peer1.conf`).
3. В клиенте включите туннель; в `AllowedIPs` клиента добавьте `172.28.0.10/32` (только DNS) или `172.28.0.0/24` (вся внутренняя сеть compose) — иначе пакет до резолвера не попадёт в туннель.
4. **DNS-сервер для VPN-клиента: `172.28.0.10` (порт 53, стандартный).** Именно этот фиксированный адрес резолвера в сети `backend` указывайте в настройках Wi-Fi/cellular телефона или ноутбука (DNS = `172.28.0.10`), когда туннель активен. Никаких перенаправлений портов или DNAT не требуется: порт 53 открыт напрямую, а адрес постоянный благодаря ipam.
5. Панель: `https://<домен-или-IP-хоста>/panel` через HTTPS-прокси (см. ниже), токен — read или admin.

### 3.4. Реальный домен и Let's Encrypt (замена внутреннего CA)

Caddyfile сейчас использует `localhost:443` + `tls internal` (работает офлайн). Для публичного домена:

1. В `docker/Caddyfile` замените адрес сайта: `panel.example.com:8443 { tls you@example.com ... }`.
2. Пробросьте порт 443 с маршрутизатора на хост (`REQKO_HTTPS_BIND=0.0.0.0` или IP LAN-интерфейса в `.env`; по умолчанию `127.0.0.1`, что подходит только для доступа с самого хоста).
3. Caddy сам получит и обновит сертификат Let's Encrypt (HTTP-01/TLS-ALPN-01).
4. DNS A-запись домена должна указывать на ваш белый IP; для динамического IP используйте DDNS.

## 4. Чек-лист перед удалённым доступом

- [ ] `.env` создан из `.env.example`, токены сгенерированы заново (`openssl rand -hex 32`), `.env` не в git.
- [ ] `REQKO_DNS_BIND` — LAN-интерфейс или `127.0.0.1`; **не** `0.0.0.0` без VPN.
- [ ] `REQKO_HTTPS_BIND` и `REQKO_WG_BIND` — по умолчанию `127.0.0.1` (доступ только с самого хоста); для реального удалённого доступа переопределить на LAN-адрес или осознанно на `0.0.0.0`.
- [ ] `REQKO_ALLOWED_NETWORKS` не содержит `0.0.0.0/0` (ACL включён).
- [ ] VPN-профиль проверен: `docker compose --profile vpn ps`, хендшейк `wg show`.
- [ ] Панель доступна только по HTTPS; сертификат внутреннего CA добавлен в доверенные или предупреждение осознанно принято.
- [ ] Резервная копия тома `reqko-data` (статистика) и `.env` (токены) хранится отдельно.
